# VPS Sentinel 1.0 開發標準

本文件是 1.0 系列的開發基準。功能規格、程式碼與發布流程若與本文件衝突，必須先用 ADR 說明並取得審查同意後才能變更。

## 1. 產品目標

VPS Sentinel 1.0 要讓使用者從一個 Home Assistant 介面監控不同供應商、不同網路位置的多台 Linux VPS，並以一致、可復原且容易理解的方式完成安裝與升級。

### 1.0 必須完成

- 多台 VPS 可註冊到同一個主控端，名稱、來源與位置不得造成識別衝突。
- 提供總覽與單機詳情；離線、資料過期、告警與正常狀態清楚可辨。
- 安裝流程統一為單一入口，支援主控端、節點端及整合安裝三種角色。
- 0.9.x 使用者能升級，既有 entity ID 與自動化不會在未告知下失效。
- 遠端操作維持最小權限、預設關閉，且不得提供任意 Shell 執行。

### 1.0 不處理

- 對外公開的 SaaS 主控平台。
- 任意遠端終端機或腳本執行。
- 非 Linux 節點代理程式。
- 未經量測就全面改寫既有功能。

## 2. 固定架構邊界

1. **Agent（節點端）**：只負責收集、健康檢查、能力宣告與傳送資料。
2. **Controller（主控端）**：管理節點清單、資料契約、Home Assistant Discovery、告警與介面。
3. **Installer（安裝器）**：負責前置檢查、角色選擇、套用、驗證、升級與復原。
4. **UI（介面）**：只使用公開資料契約，不依賴某台主機的硬編碼 entity ID。

顯示名稱可以修改；節點識別碼必須穩定且唯一。供應商、區域與標籤是中繼資料，不得作為唯一識別。

## 3. 每項工作的必要規格

任何功能進入實作前，都必須在 Issue 或 PR 說明：

- 問題與使用情境。
- 明確的完成條件與不處理範圍。
- 受影響的資料契約、安裝流程與相容性。
- 安全風險、失敗狀態及復原方式。
- 測試方式與可量測結果。
- 使用者可見變更及文件需求。

缺少其中任何一項，不得標記為 Ready。

## 4. Git 與審查標準

- 不直接在 `main` 開發；使用短期分支與 Draft PR。
- 一個 PR 只處理一個可獨立驗收的目的。
- 架構、資料契約、相容性或語言選擇先建立 ADR。
- PR 必須附上測試結果、升級影響及回復方式。
- 合併前須解決所有阻擋性意見，並通過必要檢查。
- 使用者可見變更須同步更新 CHANGELOG、安裝說明或操作文件。

## 5. 相容性與資料契約

- 1.0 契約必須有明確 `schema_version`。
- 節點至少回報：`node_id`、顯示名稱、agent 版本、能力、最後回報時間與資源狀態。
- 重新命名、修改供應商或位置不得改變 Home Assistant entity ID。
- 重複 `node_id` 必須拒絕並顯示可理解的修正方式。
- 離線與資料過期必須分開表示，不得把最後一次數值誤當成即時數值。
- 0.9.x MQTT 主題先由相容層保留；移除前必須提供遷移工具與至少一個穩定版本的公告期。

## 6. 安全標準

- 密碼、Token 與 MQTT 憑證不得寫入日誌、診斷包或 Home Assistant 狀態。
- 每個 Agent 使用可撤銷、最小範圍的憑證。
- Broker 不得預設暴露到公網。
- 遠端動作使用明確允許清單、稽核事件與逾時；預設關閉。
- 所有外部輸入均須驗證，節點名稱與標籤不得進入 Shell 指令。
- 發布產物提供 checksum；正式採用 Go 時另提供 SBOM。

## 7. 介面標準

- 首頁採「異常優先」：離線與告警置前，正常節點保持安靜。
- 總覽至少顯示狀態、名稱、來源、CPU、記憶體、磁碟、告警與最後回報時間。
- 點選節點後才能展開網路、服務、維護與歷史細節。
- 支援搜尋、狀態篩選與標籤分組；少量節點時不增加多餘操作。
- 行動裝置不得水平捲動，主要觸控區至少 44 px。
- 顏色不能是唯一狀態訊號；必須有文字或圖示。
- 明確設計載入中、無節點、資料過期、離線、部分失敗及權限不足狀態。
- 支援深色／淺色主題及減少動態效果設定。

## 8. 安裝與升級標準

唯一入口須提供：

1. 前置檢查。
2. 選擇 `controller`、`agent` 或 `combined`。
3. 在變更前顯示完整執行計畫。
4. 套用設定。
5. 自動驗證服務、連線與 Home Assistant 發現。
6. 最後只顯示一份待辦清單與診斷指令。

安裝器還必須：

- 可重複執行且不破壞既有設定。
- 支援非互動設定檔與 `--dry-run`。
- 中斷後可繼續，並保留階段化日誌。
- 能偵測既有 Broker、Home Assistant 與 0.9.x 安裝。
- Agent 加入流程使用一條可複製的註冊命令或短效註冊憑證。
- 每個變更階段都有驗證及復原方式。
- 只有 Home Assistant 本身無法自動化的操作，才允許保留人工步驟。

## 9. 品質門檻

每個相關 PR 必須依影響範圍通過：

- Python 單元測試與格式／靜態檢查。
- Shell 語法與 ShellCheck。
- YAML、JavaScript 與 Home Assistant 設定驗證。
- MQTT 契約、版本相容與重複識別測試。
- Agent 斷線、重連、Controller 重啟與資料過期測試。
- 安裝、重跑、0.9.x 升級及復原測試。
- amd64 與 arm64 的必要驗證。
- 文件中的命令與實際入口一致。

不得以「之後補測試」作為合併條件。

## 10. 1.0 發布門檻

1. 至少三台不同來源 VPS 可同時運作 7 天，無識別衝突或資料串台。
2. 一台離線或網路抖動不影響其他節點，恢復後能自動重連。
3. 0.9.x 升級後既有實體與自動化可保留，或有自動遷移與明確預覽。
4. 全新安裝、加入第二台節點與移除節點都能依單一流程完成。
5. UI 在手機與桌面可用，所有失敗狀態均有明確提示。
6. 安全檢查、效能基準、升級與復原演練均有紀錄。
7. 發布說明遵循 [發布內容標準](release-standard.md)。

以上門檻未完成時，只能發布 Preview、Alpha、Beta 或 RC，不得標記為 1.0 穩定版。
